# Warp Drive Composite Building

**Document role:** this is the maintainer reference for the Warp Drive's composite entity: its prototypes, companion ownership, electrical roles, lifecycle, wiring, and rendering. It does not specify gameplay balance, research routing, location calculations, or audio implementation. `README.md` is authoritative for player-facing behavior and values; `AUDIO.md` covers sound assets and runtime playback.

## Why It Is Composite

No single Factorio entity provides a large selectable building, continuous animation, circuit input and output, persistent charge, and a runtime-sized electrical load. The placed drive therefore consists of one visible controller and hidden companions at the same position.

The controller owns the composite. Companions are never independently placeable, selectable, minable, blueprintable, deconstructable, or colliding.

| Need | Composition choice |
| --- | --- |
| Player interaction and circuit input | Visible `constant-combinator` controller |
| Continuously blinking status lamps | Zero-power animation companion |
| Core graphics that follow the drive state | Script-owned `LuaRendering` animations on the controller |
| A positional hum while warp holds | Hidden simple entity with a looping working sound, present only during warp |
| Detector, charging, and support sampling | Runtime-configured secondary-input electric energy interface |
| Persistent warp support reserve | Serialized joule value in the drive record |
| Scripted circuit output | Hidden output combinator |

The shared power interface uses consumer-only secondary-input mode, the same priority as ordinary machines, and requests its exact current logical demand. Factorio classifies every tertiary interface buffer as accumulator storage even when it cannot output power; secondary mode keeps this interface out of the accumulator-charge display. Runtime code transfers measured charging delivery into the serialized reserve, and switching from experimental to practical mode discards detector energy so it cannot become activation charge.

## Prototype Composition

| Prototype | Type | Lifetime | Role |
| --- | --- | --- | --- |
| `bte-warp-drive-controller` | `constant-combinator` | Always | Visible 9x9 entity with the static hull and shadow; ownership anchor, health, collision, mining, circuit input, and GUI target |
| `bte-warp-drive-animation` | `electric-energy-interface` | Always | Zero-power 32-frame additive status-lamp loop |
| `bte-warp-drive-field-hum` | `simple-entity-with-owner` | During warp | Plays the looping warp-field hum around the building |
| `bte-warp-drive-power-interface` | `electric-energy-interface` | Always | Runtime-sized secondary-priority detector, charging, and support sink; prototype permits requests up to `60 GW` and forbids output |
| `bte-warp-drive-circuit-output` | `constant-combinator` | Always | Scripted practical `W`, `C`, and `S` outputs, `D`, and pre-Practical `T`, on both wire colors |

Legacy detector, support, and tiered charge-buffer prototypes remain defined only so supported saves can load and migrate their companions and stored energy.

Ten `animation` prototypes, `bte-warp-drive-<state>-interior` and `bte-warp-drive-<state>-glow` for the `standby`, `detecting`, `charging`, `activation`, and `warp` states, hold the core overlays.

## Rendering And Wires

All drive graphics are generated by `tools/sprites/render.mjs` from `tools/sprites/models/warp-drive.js` into `graphics/entity/warp-drive/`, each sheet with the `.lua` metadata `util.sprite_load` reads; re-export them instead of editing the files. The controller draws the static hull and its shadow, which also serve as the placement preview. The animation companion draws the status lamps on `higher-object-under`.

Everything that changes with the drive state lives in `scripts/visuals.lua`. It keeps two `LuaRendering` animations targeted at the controller, also on `higher-object-under`: a normally blended interior (glass tube, rings, nozzles, and core thread, already cut where the ribs pass in front) and an additive glow (plasma, ring nodes, conduits, projectors, and light on the deck). Each 10-tick update maps the record to a visual state and replaces both objects when it changes:

| Record state | Visual state | Playback |
| --- | --- | --- |
| `detector-offline`, `idle`, `cooldown` | `standby` | Static interior; glow loop at 0.25 frames per tick |
| `detecting` | `detecting` | The charging animation in green; 0.25 to 1 frame per tick, glow tint from 45% to 100%, both by detector power |
| `charging` | `charging` | 0.25 to 1 frame per tick, glow tint from 45% to 100%, both by reserve progress |
| `warp`, first 90 ticks after entering from `standby` or `charging` | `activation` | 30 frames over 90 ticks, started on frame 0 to match `warp-activation.ogg` |
| `warp` | `warp` | Interior (turning rings) and glow loop at 0.5 frames per tick |

`LuaRendering` shows frame `tick * speed + offset` modulo the frame count, so a speed change recomputes the offset to keep the current frame and avoid a jump. Speed and tint are reissued only when they change by more than 2%. Render objects targeted at the controller disappear with it; the record keeps `visual_interior`, `visual_glow`, `visual_state`, `visual_speed`, `visual_glow_level`, and `visual_activation_until`, and `rebuild_drives` resets them so changed prototypes are redrawn on the next update.

During warp, short-lived cyan streaks glide south across the field. A harmless clone of Space Age's Fulgora lightning prototype provides its full procedurally forked bolt, eight ground-streamer variants, shader layers, and native 36-tick lifecycle while removing the endpoint explosion, damage, attractor energy, sound, camera flash, debris, and smoke. Cached platform foundation bounds, expanded by 128 tiles on each side, define the shared streak and anomaly field, enough to fill the most zoomed-out game view around a ship; streaks scale with its area, one per 512 tiles (48 to 900), working in freely panned remote view. Tile events refresh the bounds without scanning in the 10-tick update. Whole strikes start at randomized moments rather than being seeded partway through an animation.

A lightning entity draws its cloud at its own position and its bolt `source_offset` tiles south of it, 25 tiles for the Fulgora clone. Lightning strikes only around the drive: about once every 1.7 seconds a strike lands its bolt anywhere within 10 tiles of the drive, its cloud 25 tiles north of the landing point. Open space in the field gets no lightning.

Streaks are `bte-warp-drive-streak` particles, which the engine moves every tick, so they glide instead of stepping with the 10-tick update. Each update only spawns about enough at random places to keep one streak per 512 tiles of field alive (48 to 900), over a 120-tick life at 0.555 tiles per tick. Spawn points extend one life's travel north of the field so its north edge is as dense as the rest. They always head south with their bright head leading, the way the game's starfield streams past a travelling platform, whichever way it goes. Their sheet, from `tools/sprites/models/warp-field.js`, has four shapes (a clean line, a broader soft one, one with a faint twin, and a gently beaded one), each a row of eight frames that fades in over the first two and then holds; the particle plays its row once over its life, so new streaks fade in rather than pop up, and fade away at the end. Sixty variations combine the shapes with five light blues and three lengths. Particles cannot be listed from scripts, so the runtime test does not count them; the prototype test pins their variations and flight.

Lightning's cloud is the `nebula` sheet of `tools/sprites/models/warp-field.js`, eight frames of one cloud's life drawn as additive glow in neutral white, tinted a dim blue-grey so strikes do not flash colour.

The colourful background is `scripts/anomalies.lua`, independent of the lightning. While warp holds it keeps one anomaly per `36 x 36` tiles of the field (at most 250), each two shapes from the six-frame `anomaly` sheet drawn with `LuaRendering.draw_animation` (`animation_speed` 0) on `under-tiles`, so the deck hides them. Every 10-tick update moves each anomaly along its slow drift, eases its scale between two sizes, turns each shape, crossfades between the two shapes so its form changes, shifts its pastel hue, and fades it in and out over its 30 to 60 second life; expired anomalies are replaced. The first fill starts each anomaly part-way through its life so they never fade together, and the whole field fades in at entry and out over 120 ticks after exit. Space platforms are always day, so the clouds read as lit through additive glow rather than light sources. Render objects expire on their own shortly after their anomaly would end, and removing the drive destroys them.

The activation shockwave continues across the platform as trivial smoke, which the engine grows and fades without script updates. Warp entry records `shockwave_tick`; the warp effect update sends an azure ring 30 ticks later, with the core's flash, and a violet ring at 40 ticks, counting them in `shockwaves_sent`. Each ring grows from the building's 4.5-tile edge, where the model's own shockwave fades, to the smallest of four prototype reaches (32, 64, 128, or 256 tiles) that covers the platform's foundation bounds from the drive. Smoke stays drawn while its centre is off screen, so the ring is visible across large platforms.

Drive audio is owned by the warp lifecycle. Event sounds play ship-wide without an
entity; only the positional field hum needs one, the warp-only companion above, which the
warp sound update creates and removes. See [`AUDIO.md`](AUDIO.md) for assets, runtime
scheduling, persistent state, and regeneration.

The symmetric footprint reuses one circuit connection definition in all directions. When adjusting it:

- The endpoints are the insulator tips of the circuit terminal south-west of the dais; derive new ones from the model's coordinates (`shift = (x, z - y * cot 50°)`, shadow `(x + y, z + 0.25 * y)`).
- Keep red and green endpoints ordered like vanilla entities to avoid crossed wires.
- Move each endpoint with its matching shadow point.
- Validate attachment, sag, and overlap in game.

## Runtime Ownership

`storage.drives` is keyed by `LuaSpacePlatform.index`. Each platform may own one record and one controller.

| Field | Role |
| --- | --- |
| `entity`, `platform_index` | Controller reference and platform identity |
| `animation`, `power`, `circuit_output`, `field_hum` | Active companion references; `field_hum` exists only during warp |
| `activate`, `deactivate`, `detector_start`, `detector_stop` | Independent circuit conditions `{enabled, first_signal, comparator, second_signal, constant}` for warp engagement and the detector; a disabled condition or one without a first signal is never true, and each stop condition wins over its start condition |
| `detector_on` | Detector latch for research acceleration and, after Practical research, the Tachyon Science Boost; set by the Start and Stop buttons and, while true, by the detector conditions; defaults on |
| `output_*_enabled`, `output_*_signal` | Independent circuit output toggles and signal assignments; legacy outputs default enabled and distance defaults disabled |
| `state`, `cooldown_until` | Composite state and lockout |
| `last_distance`, `direction` | Travel samples used by movement logic |
| `detector_power`, `detector_power_ratio`, `detector_request_watts` | Latest detector sample, factor relative to `200 MW`, and adaptive next demand |
| `warp_level`, `requested_warp_level`, `warp_target` | Current, probed, and sustainable warp levels |
| `reserve_energy`, `migrated_reserve_energy` | Authoritative private reserve and one-time legacy energy capture |
| `support_power`, `power_sample_watts`, `power_sample_support_watts`, `support_demand_watts`, `support_check_after` | Delivered power, interface request, logical warp demand, and startup grace |
| `warp_ramp_state` | GUI acceleration status |
| `lightning_bounds` | Active warp effect footprint |
| `anomalies`, `anomaly_field_since`, `anomaly_field_until` | Background anomalies (drift, scale, hue, shapes, render objects) and the field's fade-in and fade-out start ticks |
| `shockwave_tick`, `shockwaves_sent` | Warp entry tick for the pending activation shockwaves, and how many were sent |
| `visual_*` | Core overlay render objects and their current state, speed, and glow level |

Build events call `register_drive`. Invalid off-platform placement is destroyed. A duplicate controller is destroyed, refunded on the platform surface, and reported to the force.

Companion invariants:

- Every companion shares the controller's surface and exact position. Companions are created with `snap_to_grid = false`, since the zero-size companions would otherwise snap to a tile corner while the odd-sized controller sits on a tile centre.
- A valid stored reference at that position is authoritative.
- `find_companion` recovers a missing reference locally and removes same-position duplicates.
- Broad orphan scans run only during registration or rebuild, never during the 10-tick update.
- Mining, death, scripted destruction, and invalid-record cleanup remove companions through stored references.

`rebuild_drives` reconstructs records from controllers during initialization and configuration changes. It removes orphans and duplicates, adopts valid companions, recreates permanent companions, and discards the removed detector-power output fields.

## Electrical Lifecycle

### Detector

The `detector_on` latch gates the shared power interface before Practical research, and while the drive is `idle` after it. While enabled, it adaptively requests up to `1 GW`. Every 10 ticks, runtime takes the delta of the interface prototype's cumulative electric-network input and converts those consumed joules to average delivered watts:

```text
delivered watts = consumed joules * 60 / elapsed ticks
```

The result is capped at `1 GW`. After a shortfall greater than `0.1 MW`, the next request drops to measured delivery. When the request is fully supplied within that absolute tolerance, it increases by `10 MW`. This feedback converges near generation left over after ordinary ship demand while continuing to probe changing capacity. Research scales against a `200 MW` reference, so the power factor ranges continuously from `0` to `5`. The interface's zero output limit prevents sampled energy from powering the ship.

### Charge

After Practical research, detector energy and sampling state are discarded and the same interface enters practical mode. It serves the detector only while `idle`; engaging discards the last detector sample, so detector energy is never credited to the reserve, and charging, warp, and the lockout pause it. `LuaSpacePlatform.weight` is already kilograms at runtime, so required reserve is exactly `platform.weight * 100 J/kg` with no data-stage gram conversion. `record.reserve_energy` is authoritative; the interface buffer is only a short-lived electrical sample and never stores or outputs the reserve. Once engaged, and while minimum speed, active travel, endpoint clearance, and cooldown all permit entry, an incomplete reserve makes the interface request `platform.weight * 10 W/kg`; runtime code converts measured delivered watts into joules every 10 ticks and caps the private reserve to the mass-scaled requirement. Losing any prerequisite disables the request and resets the reserve to zero. Full delivery therefore charges an empty reserve in 10 uninterrupted seconds. Warp entry spends 90% of that charge and retains 10% as support reserve. During warp, up to the same `10 W/kg` rate replenishes the reserve after support demand is satisfied. A current-level support deficit drains it in proportion to the shortfall; a complete outage lasts 1 second immediately after entry or 10 seconds once fully replenished.

### Support

Once every non-reserve entry requirement is satisfied, the interface requests `platform weight in kg * 10 W/kg`. Losing any prerequisite disables that request immediately and clears the private reserve, preserving the uninterrupted charging challenge and transition. Once the audible buildup has started, interruption also starts a 300-tick re-entry lockout through the existing `cooldown_until` mechanism. During warp it requests the next level's support demand plus up to `platform weight in kg * 10 W/kg` to replenish missing reserve energy. Runtime electric-flow fields use joules per tick, so watt values are divided by `60` when setting `power_usage` and `input_flow_limit`. The GUI reports the drive's measured total electrical consumption, including support and reserve replenishment, in one checklist row.

The interface has a one-tick buffer and consumes continuously. Electric statistics report the interface prototype's actual cumulative consumption; one drive per platform makes each interval delta unambiguous even when Factorio relates multiple electrical subnetworks. Runtime resets the baseline when the interface changes subnetworks. Secondary-input mode also keeps the buffer out of Factorio's accumulator-charge totals. The interface cannot output to the ship. Runtime allocation satisfies sampled support demand first and transfers only additional delivered power into the reserve. Two update intervals of startup grace let Factorio attach and service a newly configured sink before the first shortfall check. During a brownout, Factorio proportions available power across the drive and other secondary consumers normally. At least 99.9% delivery of next-level demand permits acceleration. Delivery below current-level demand holds the current level and drains reserve. Depleting the reserve exits warp.

### Companion States

| State | Companion effect |
| --- | --- |
| `detector-offline`, `detecting` | Power interface samples detector demand; `detecting` also covers the idle Tachyon Science Boost |
| `charging` | Engaged before entry: power interface samples delivered charging power into the private reserve |
| `idle` | Power interface serves only the detector, when its latch is on, until Engage or a true activate condition finds every non-reserve entry requirement met |
| `warp` | Power interface samples support plus reserve-replenishment demand |
| `cooldown` | Power interface is disabled and the private reserve remains empty |

Research revocation while active exits warp, clears the private reserve, and reconfigures the interface for detector mode. Any warp exit disables the interface request and starts the 600-tick lockout. Disengage, a true deactivate condition, route loss, and endpoint clearance exit immediately; Disengage or a true deactivate condition during charging is an interrupted activation. Every exit returns to `idle`, so the next jump needs Engage again or a true activate condition. Engine speed below `50 km/s` instead starts a 300-tick warning while retaining Warp-1; recovery cancels the warning, otherwise expiry exits with an insufficient-speed reason. Runtime warning and last-exit reason fields drive the window header's status line.

## Circuit Composition

The visible controller reads the activate and deactivate conditions. Engage and Disengage call the same entry and exit paths as the conditions, and Engage runs the first charging step immediately so the buildup answers the click. The hidden combinator owns configurable output slots and is script-connected to both controller wire colors. The window keeps each tab's conditions beside the state they control: warp conditions on the Warp tab, detector conditions on the detector tab, and network status and outputs on the Signals tab. Rendering indexes the window's elements by their unique names and redraws the whole window when a required element is missing or `layout_version` changes, so saved GUIs from older versions are replaced rather than indexed. The selected tab is remembered per player in `storage.gui_tabs`.

| Default signal | Output |
| --- | --- |
| `W` | Completed integer warp level while engaged, otherwise `0` |
| `D` | Whole kilometres remaining to the active connection destination |
| `C` | Warp support reserve percentage, capped at `100` |
| `S` | Effective integer speed |
| `T` | Whole tachyon particles per second at the current route depth |

Every output is independently enabled and signal-selectable. `W`, `C`, and `S` remain enabled on existing records; `D` and `T` are opt-in. Research mode hides and suppresses `W`, `D`, and `S`; `T` is available in both modes. The removed detector-power output is not serialized or emitted. The Warp tab and the header derive their engagement checklist and blocker from the same runtime predicates used by entry and exit, including destination identity and remaining connection kilometres for endpoint clearance. Blueprint tags and settings paste preserve all four conditions and the output settings, but not the engaged state or detector latch. Records from before these conditions are migrated once: a legacy circuit condition becomes the activate and detector start conditions with its exact inverse as the deactivate and detector stop conditions, preserving its level-triggered behaviour, and legacy automatic control becomes manual. Opening the controller is intercepted for the custom GUI unless the cursor holds a wire, planner, blueprint, or other tool.

## Validation

After changing composition prototypes or lifecycle code, from the repository root:

1. Run `./make.sh warp-drive`.
2. Run Factorio with `--dump-data` and inspect resolved prototypes.
3. Run `./warp-drive/tests/run-runtime-tests.sh`.
4. Run `git diff --check`.

The scripted suite covers placement, duplicate rejection, companion recovery and cleanup, electrical transitions, circuit output, research revocation, and relocation. Interactive checks remain necessary for electrical behavior, graphics, GUI interception, robots and ghosts, and wire geometry.
